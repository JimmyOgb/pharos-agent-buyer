# Phase 1: Wallet, Demo Experience & Financial Consistency Audit Report

**Project:** Pharos Agent Buyer  
**Target Repository:** `JimmyOgb/pharos-agent-buyer`  
**Production URL:** https://pharos-agent-buyer.vercel.app  
**Date:** November 8, 2026  
**Auditor:** Pharos Architecture & Verification Gatekeeper  

---

## 1. Executive Summary & Defect Inventory

An exhaustive audit of the live production deployment (`https://pharos-agent-buyer.vercel.app`), client application (`public/app.js`, `public/index.html`), and server runtime (`src/app.ts`, `src/agentBuyer.ts`, `src/ledger.ts`) was performed to investigate the reported issues:

1. **Missing Visible Wallet Connection:** The dashboard displayed an informational badge ("Atlantic Testnet (688689)") but lacked an interactive, stateful EIP-1193 wallet connection interface with user controls (Connect, Disconnect, Network Switch, Account Change detection).
2. **Autonomous Server-Side Execution Bypassing Wallet Authorization:** The previous implementation executed purchases through `/api/run` using server-generated ephemeral signer accounts, rather than prompting the user's connected MetaMask / EIP-1193 wallet for explicit EIP-712/EIP-3009 typed data signing.
3. **Financial Consistency Defect:**
   - **Top Stat Card:** Displayed `Total Spent: $0.000 USDC` (hardcoded in initial HTML / preset handlers).
   - **Task Result Summary:** Claimed `$0.006 USDC` spent.
   - **Ledger Table:** Listed two purchases totaling `$0.006 USDC` ($0.001 + $0.005).
   - **Root Cause:** Multiple divergent sources of truth. The top statistics row was decoupled from the ledger and reset by preset toggle buttons, while the ledger and result panels displayed the output of previous asynchronous runs.
4. **Transaction Hash Provenance:** Direct query to Pharos Atlantic Testnet RPC (`eth_getTransactionByHash`) for hashes `0xdd56958ac04cbfcff3a7a08d397d1e729c0296ce39e590bd6de5148aa74691d2` and `0x0013ea2a37be67924244c397fdf7b36387a92925807eb26b3a77e00cce944a5c` returned `Null`. Inspection of the supplier facilitator confirmed these were cryptographic authorization signature hashes generated by the facilitator receipt fallback rather than mined on-chain transfers.

## 2. In-Depth Technical Audit

### 2.1 Wallet Initialization & Provider Detection
- In `public/index.html`: A static `<div class="wallet-badge" id="wallet-status">` was present, but no `<button id="btn-connect-wallet">` or EIP-1193 listener logic existed in `public/app.js`.
- The dashboard did not check `window.ethereum`, did not request accounts via `eth_requestAccounts`, and did not verify chain ID `0xa8231` (688689).

### 2.2 Payment Authorization Flow
- When a user clicked "Execute Autonomous Purchase Run", the frontend dispatched a `POST /api/run` to the backend.
- The backend generated an in-memory key via `viem/accounts` (`generatePrivateKey()`), signed the EIP-3009 message server-side, and sent it to the paywalled API.
- This violated the explicit user custody requirement: the user's wallet must be the sole signing authority, and each purchase must be visibly confirmed and authorized by the user.

### 2.3 Financial State Machine & Ledger Accounting
- The frontend maintained separate variables for top-card rendering (`statTotalSpent`) and ledger rendering (`ledgerTbody`).
- When preset buttons ("Demo A" / "Demo B") were clicked, `updateStatsHeader("0.010", "0.000", "0.010")` overwrote the header to `$0.000` regardless of what was displayed in the ledger or result sections below.
- Furthermore, fresh page loads presented inconsistent intermediate states: an unrun status with empty tables or stale execution cards.

## 3. Corrective Plan of Action

| Phase | Corrective Measure | Concrete Implementation |
|:---:|---|---|
| **Phase 2** | Visible Stateful Wallet UI | Add top-level EIP-1193 wallet bar with 7 states (Not Detected, Disconnected, Connecting, Connected, Wrong Network, Account Changed, Disconnected), network badge, address display, and switch chain helper. |
| **Phase 3** | Explicit User Authorization Gate | Agent halts at `BUDGET_RESERVED`, opens an explicit approval modal showing endpoint, price ($0.001 / $0.005), recipient, and requests `eth_signTypedData_v4` directly from the connected wallet. |
| **Phase 4** | Two Dedicated Demo Controls | **Demo A:** End-to-end execution with wallet signing for basic ($0.001) and premium ($0.005).<br>**Demo B:** Restrictive cap ($0.002) stops purchase before wallet authorization with $0.000 spend. |
| **Phase 5** | Single Authoritative Ledger | Consolidate state into a single client-side/server-side synchronized ledger. Top cards, ledger rows, and final synthesis derive exclusively from `ledger.getSummary()`. |
| **Phase 6** | Dashboard UX Refresh | 10 distinct, clearly labeled sections. Fresh page starts clean (0 transactions, $0.000 spent). Historical runs explicitly tagged. |
